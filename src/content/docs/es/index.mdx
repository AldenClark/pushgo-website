## Por qué PushGo

<CardGrid stagger>
  <Card title="Tres modelos de datos" icon="document">
    Message sirve para notificaciones puntuales. Event describe un ciclo de vida actualizable. Thing mantiene el estado actual de un dispositivo, servicio o trabajo.
  </Card>
  <Card title="Entrega nativa" icon="rocket">
    Los clientes Apple reciben notificaciones del sistema mediante APNs. Los clientes Android pueden combinar FCM con transportes privados para una sincronización más flexible.
  </Card>
  <Card title="Autoalojamiento" icon="setting">
    Gateway puede ejecutarse en su propia infraestructura con base de datos persistente, autenticación de Gateway, transportes privados, observabilidad y soporte para reverse proxy.
  </Card>
  <Card title="Campos cifrables de extremo a extremo" icon="heart">
    El contenido sensible puede colocarse en `ciphertext` y descifrarse localmente en el cliente. Gateway autentica, retransmite y distribuye sin necesitar entender el contenido en claro.
  </Card>
  <Card title="Migración gradual" icon="star">
    Los endpoints compatibles con ntfy, Bark y ServerChan permiten conservar scripts existentes mientras migra gradualmente a los modelos nativos de PushGo.
  </Card>
  <Card title="MCP/OAuth" icon="random">
    Gateway puede actuar como MCP HTTP Server. Los asistentes de IA pueden enviar Message, administrar Event y actualizar Thing dentro del alcance de canales autorizados.
  </Card>
</CardGrid>

## Petición mínima

```bash
curl -X POST https://gateway.pushgo.dev/message \
  -H "Content-Type: application/json" \
  -d '{
    "channel_id": "YOUR_CHANNEL_ID",
    "password": "YOUR_CHANNEL_PASSWORD",
    "title": "Hello from PushGo",
    "body": "This is a test notification."
  }'
```

Continúe con [Empezar](/es/guides/getting-started/) para enviar esta petición con un canal real.
